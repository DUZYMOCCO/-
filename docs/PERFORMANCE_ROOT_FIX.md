# 戦闘の停止・ぎくしゃくした移動・負荷の修正

2026-10-07 / v1.24.4 / Service Worker v66

## 発見した根本的な不具合

### 1. 戦闘更新が毎フレーム例外で中断

`update()` で `BASE_TERRITORY_RADIUS` を使ってから、同じ関数内で `const` 宣言していた。
実際に更新処理を実行し、`ReferenceError: Cannot access 'BASE_TERRITORY_RADIUS' before initialization` を再現した。
フレームループは例外を捕捉して次のフレームを再予約しており、戦闘と描画に到達できないまま、時計など前半の処理だけを繰り返す構造だった。

定数宣言を最初の参照より前へ移した。予期しない例外が残った場合も無限に再試行せず、ゲームを停止して再開手順を表示する。失敗したフレームの状態を自動保存しない。

### 2. AI間引きが移動方向を変えていた

軽いフレームでは隊列位置へ移動し、通常フレームでは近い敵に接近していた。
そのため、FPSが高くても近接中の兵士が敵と隊列の間を往復する可能性があった。
360以内の敵と交戦中は移動・攻撃を連続更新するよう変更。遠い敵の再探索キャッシュは維持する。

### 3. AIキャッシュが保存データを循環させる

兵士の `_cachedEnemy` が敵を参照し、敵の `_cachedTarget` が兵士を参照し返す。
この状態で兵士配列をそのままJSON化すると循環参照で失敗する。
保存用コピーから `_` 始まりの実行時フィールドを外した。兵士の装備・成長・位置・搬送関係と、休息中の敵の残HPは保持する。

## 人数を維持した負荷対策

本隊48名、直属上限12名、敵上限40体、補充間隔0.85秒を変更していない。これらは作業開始時点の現行設定。

- 画面外の拠点・本陣・宝箱は描画処理を呼ばない。存在やシミュレーションは削除しない。
- 半径数万の境界破線円は、画面に映る短い円弧だけを描く。画面外なら線を生成しない。
- 地形キャッシュを72→24タイルへ制限。512×512の画素分の保持量は約72→24MiB。世界の広さ・景観密度・可視範囲を変更せず、捨てたタイルは同じ地形へ再生成する。
- 会議・地図などの停止中は戦場を再描画し続けない。開閉とリサイズ時には更新する。
- 兵士・敵の姿と近接の動きは描き続ける。人数・戦果・秘宝の抽選率をさらに削る変更はしていない。

木などの画像キャッシュも試したが、ソフトウェアCanvasで中央値38.75msと遅くなったため撤去した。
現在の修正にはそのキャッシュを含めていない。

## 実行計測

ブラウザ操作接続は今回利用不可（利用可能ブラウザ0件）。iPhone実機FPSは測れていない。
同じ描画コードを、同梱の `@napi-rs/canvas` で動くソフトウェアCanvasに接続し、48兵士＋40敵の密集戦闘を実行した。
ウォームアップ20フレーム、その後100フレームを測定。乱数種を固定し、同じ位置と人数で比較した。

比較用の修正前コードには、実行を可能にするため定数宣言順の修正だけを先に適用している。
生の修正前コードは更新途中で例外になり、正常な描画時間を測定できなかった。

| 指標 | 比較用修正前 | 修正後 |
|---|---:|---:|
| 最終再計測のフレーム処理中央値 | 12.177ms | 11.934ms |
| 最終再計測の95パーセンタイル | 13.034ms | 12.841ms |
| 画面外拠点の描画処理の合計/フレーム | 0.592ms | 0ms |
| 人数 | 48＋40 | 48＋40 |

先の固定乱数計測では12.603→11.742msだった。実行環境によるばらつきがあり、通常描画の短縮は小幅。iPhoneで同じ値やFPSになる保証はない。
今回の主な修正は、更新の例外停止と移動の逆戻りを取り除くこと。

生データ：`PERF_BASELINE.json` / `PERF_CURRENT.json`。
ローカルの再現用fixtureは `__pycache__/bench.mjs` と `__pycache__/perf-review.html`。保存をメモリに隔離し、実セーブにはアクセスしない。比較用コードは同フォルダ内に一時保存してある。
